# 自动化任务

在侧栏打开「自动化任务」，填写任务名称、商品标识、匹配方式、国家与店铺，再选择日期范围、运行星期与时间。默认星期为周一至周六，时间为 09:00；这只是编辑器默认值，保存前不会创建任务。

每个任务可以设置不同的星期、时间与筛选条件。「使用当前采集条件」会复制采集页的条件和固定日期；若希望日期自动向前滚动，复制后请改选动态日期范围。

保存任务后，点击「启用定时运行」。Windows 按不同执行时间注册当前用户的计划任务，Mac 将星期、时、分写入当前用户的 LaunchAgent。到设定时间才启动调度，不再每分钟启动空检查。例如 08:00 与 18:00 各触发一次；同一时刻的多项任务一起发起。

定时总开关启用后，新增任务、修改时间或星期、停用和删除任务都会同步更新系统计划；只修改商品条件时复用已有触发时间。所有任务都停用时移除系统触发，保留总开关状态，之后保存启用任务会重新创建触发。启用或编辑时系统同步失败会报告错误并恢复此前配置和计划；若系统也拒绝恢复，会明确提示暂停后重新启用。点击暂停会立即关闭总开关，即使系统拒绝移除触发器也不会继续发起采集，并报告清理失败。

关闭主窗口后仍可执行；电脑必须保持开机、已登录且未休眠，Chrome 需要已安装。使用电脑本地时区，运行时间精确到分钟。错过的分钟不补跑；暂停后也不会补执行过去的任务。

「暂停定时运行」停止后续定时触发，已经开始的采集继续完成。「立即运行选中任务」与「同时运行全部启用任务」不受定时总开关影响。编辑或删除任务不会中断已启动的那次采集。

## 日期范围

- 今天、昨天：对应本机日历日期；今天的数据可能不完整。
- 近 7 / 30 天：包含今天。
- 前 7 / 30 天：截至昨天，不包含今天。
- 本周：本周周一至今天；上周：上一个完整周一至周日。
- 本月：本月 1 日至今天；上月：上一个完整自然月。
- 固定日期区间：每次都使用填写的相同起止日期。

动态日期在每次触发时计算；例如每周一采集「上周」，会读取刚结束的周一至周日，而不是永久保存创建任务那天的日期。

## 并发与登录

程序不设置任务数和并发数上限。到期任务会全部发起，每次运行使用独立 Chrome 进程与浏览器上下文，不共用正在运行的专用 Chrome 配置目录。实际能同时完成多少取决于电脑内存、CPU、网络和领星服务；资源不足、账号登录限制或服务拒绝会作为失败记录显示。

自动任务只读取手动采集保存的 Cookie、localStorage 与 sessionStorage，不覆盖共用登录文件和私有请求模板。首次使用请在采集条件页手动完成一次采集。登录过期时，运行记录提示重新手动登录并采集，再重跑失败任务。自动采集保持有界面的 Chrome。

## 结果与排错

每次采集仍写入 `results/browser-*.json` 与配对的业务数据文件，可在原有「历史记录」和自动化运行记录中查看。每个并发结果名增加唯一标识，避免同毫秒完成时互相覆盖。

任务配置和运行记录位于数据目录的 `.private/automation/`，其中 `tasks.json` 为配置，`runs/` 为运行记录，`logs/` 为每次运行的日志。一个任务失败不取消其他任务。运行记录显示全部活动任务与最近 100 条记录，旧文件仍保留在本机。

Windows 系统任务名称以 `LingxingSearch-Automation-` 开头，末尾的四位数字表示执行时分；不同数据目录使用不同名称。同一时间合并任务所需的星期，执行时仍逐项检查任务的启用状态与星期，不会让其他日期的任务提前运行。启用后请保持应用目录位置不变；搬动目录后应重新启用定时运行。Mac 请先把应用放在固定位置，再启用；更新后若应用位置改变也需要重新启用。

Windows 定时运行通过应用 EXE 的无界面入口启动，并隐藏后台 Node 进程，不弹出命令窗口。更新后打开 PulsarFetch 会按保存的任务配置同步系统计划，换用按设定时间触发的入口并移除旧的每分钟检查任务，不重写任务内容与启用状态。同步失败会在任务页显示原因；启动或调度失败写入 `logs/scheduler-error.log`，系统计划任务保留失败退出码。

采集任务负责定时采集与结果留档。库存和站内信提醒使用独立的监控设置与后台计划。

## 批量任务与分组

`automation/cli.cjs` 的 `batch-preview` 接受 `{task,values,countries,group}`，按商品与国家组合预览，返回 `{tasks,count}`。重复的商品与国家组合会合并。`save-batch` 校验整个批次后一次保存，保留已有任务标识与字段，返回常规自动化快照；系统计划同步失败时整批恢复。

任务可带 `group` 字段。`set-enabled` 接受 `{ids,enabled}`，一次启停选中任务并同步计划，不修改商品条件；无效标识会使整个操作失败。

## 今日任务与补采

`dashboard` 返回 `{date,expected,success,failed,running,missing,items}`。每个任务的原计划日期与时间构成一次逻辑执行，同次重试按最新记录计一次。`items` 中的状态包括 `success`、`failed`、`running`、`missing`、`future`、`paused`。未到时间为 `future`，暂停的未执行任务为 `paused`，均不计入缺失；暂停后的已有运行仍保留。手动运行不抵扣计划缺失，补采过去日期也不抵扣今天的缺失。今天已执行的原时段不会因编辑或删除任务而消失。

`backfill` 接受 `{ids,scheduledDate:'YYYY-MM-DD'}`，使用本地原计划日期解析相对日期，保存 `trigger='backfill'`、`scheduledDate`、`scheduledTime` 和已冻结的 `dates`。例如补采 2026-01-01 的「前 7 天」固定读取 2025-12-25 至 2025-12-31。不会修改任务定义，也不受采集总开关影响。未来日期、无效日期和所选任务没有计划的星期会在启动任何任务前拒绝。

## 独立后台监控计划

`sync-schedule` 同步采集与监控两类计划。监控间隔来自 `monitoring/core.cjs.getSchedule(dataRoot)`，为启用提供方中的最短间隔，至少 5 分钟。暂停采集不会暂停仍启用的监控。

Windows 使用原采集计划名称附加 `-Monitor` 的独立任务，通过 `PulsarFetch.exe --monitor-tick --data ROOT` 进入后台入口。该任务首次约一分钟后运行，之后按间隔重复，重叠时忽略新实例。原采集计划仍按星期与准确时间运行，并保留并发设置。Mac 使用独立 `-monitor.plist` LaunchAgent，以 `StartInterval` 调用 GUI 可执行文件的相同入口；原采集 LaunchAgent 保留 `StartCalendarInterval`。

监控入口由桌面宿主管理，不需要主窗口保持打开。测试使用临时目录与模拟系统注册，不注册或移除真实计划。
